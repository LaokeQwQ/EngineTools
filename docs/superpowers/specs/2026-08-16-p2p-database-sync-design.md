# EngineTools P2P 传输与数据库同步设计

## 1. 目标

在同一账号的两台在线设备之间提供用户手动触发的数据库同步：优先使用 P2P，失败时使用 S3 中转；普通同步执行可选择类别的源优先、无删除合并；强制同步执行可恢复的完整覆盖。

客户端不会为了设备同步而在启动、登录或心跳时上传数据库或歌曲。设备列表自动展示身份和在线信息；同步用数据库探测只在用户点击同步后发生。用户显式开启且已经到期的自动周备份可在启动后上传完整备份，但它是独立功能，不作为未经确认的同步源。

## 2. 前置条件

- 两台设备属于同一 OIDC 用户且会话有效。
- 两台设备均在线并保持 WebSocket 心跳。
- 目标设备没有其他数据库写任务。
- 客户端协议版本可协商。
- 普通同步的数据库 schema 由同一兼容 adapter 支持。

任一设备离线时同步按钮不可用。不排队，不使用旧快照代替当前数据库。

## 3. 信令与 P2P 探测

中心服务通过 WebSocket 转发 offer、answer 和 ICE candidates，并校验双方用户、任务和设备状态。每台设备使用已注册 Ed25519 key 签名任务 ID、双方设备 ID、任务 nonce 和本端 DTLS fingerprint；对端使用认证 API 返回的设备公钥验证，防止信令替换把错误设备加入任务。

ICE 顺序：

1. host candidate，用于同一局域网直连。
2. 自建 Go STUN 服务，默认 UDP 3478。
3. 部署配置的公共 STUN 备用列表。

不使用 TURN。双方先建立 Pion WebRTC DataChannel，并完成带任务 nonce 的双向 ping、最大消息协商和短时吞吐探测。只有探测成功才让源端生成数据库快照。

探测超时、对称 NAT、企业防火墙、DTLS 失败或吞吐低于部署阈值时选择 S3。传输中 P2P 不可恢复时也切换 S3，而不是让任务整体重新开始。

## 4. 分块传输协议

P2P 和 S3 共用版本化 transfer manifest：

- 每个逻辑对象分为默认 16 MiB 校验块。
- DataChannel 内使用不超过协商上限的帧，默认 64 KiB，并携带对象 ID、块号、帧偏移和任务 nonce。
- 每个块和完整对象均使用 SHA-256。
- 接收端只确认完整且哈希正确的块。
- 流控依据 DataChannel buffered amount 和目标磁盘写入速度，不把整个对象读入内存。

切换 S3 时，目标上报已验证块位图。若完整对象尚不在 S3，源仍需上传该完整对象；目标随后用 Range GET 只下载本地缺失块。若账号备份对象库已经存在相同完整对象则直接复用。S3 不负责把仅存在于目标本地的块拼接成新对象。

临时中转对象具有短 TTL，与长期云备份对象隔离。任务完成或取消后服务端发起清理，S3 生命周期负责最终兜底。

## 5. 点击同步后的预检

用户选择远端设备后，客户端现场请求双方提供：

- Engine DJ 和应用版本。
- SQLite schema 指纹。
- 数据库、WAL 和相关资产的有效本地修改时间。
- 上次共同 revision 和父快照哈希。
- 曲目和所选类别统计。

文件修改时间只显示为估算值。若存在共同 revision，则通过父快照关系判断分叉；没有共同 revision 时，时间只用于推荐“较新源、较旧目标”，绝不自动执行或决定冲突。

推荐真值表固定为：A 的有效修改时间为 10:00、B 为 08:00 时，UI 推荐 A 为源、B 为目标；若用户选择反向仍可手动执行。时间相同、时钟不可信或双方 hash 均已变化时不推荐方向。这里的“较旧优先”表示较旧设备优先作为待更新目标，不表示旧数据库自动覆盖新数据库。

## 6. 同步模式与方向

### 6.1 普通同步

用户每次选择参与类别，默认勾选全部可移植内容：

- 曲目元数据。
- 播放列表层级、成员和顺序。
- Hot Cue、Saved Loop。
- Beat Grid、BPM、Key 和受支持分析数据。

本机路径、缓存、偏好、播放历史、设备状态和未知表默认不参与。

### 6.2 强制同步

支持双向，默认方向为“选中远端设备 -> 当前设备”。用户可显式交换源和目标。

强制同步不做记录级合并，使用源端完整数据库和所选资产覆盖目标。兼容 schema 正常执行；不兼容 schema 默认阻止，但用户可进入高级风险流程。

## 7. Schema adapter

每个受支持的 Engine DJ schema 由显式 adapter 描述：

- schema 指纹和兼容范围。
- 可移植实体、表和字段映射。
- 主外键依赖和写入顺序。
- 规范化读取、实体匹配和验证查询。
- 数据库路径重写规则。
- 版本化 fingerprint 算法和目标 Engine DJ 可读取的兼容矩阵。

普通同步只允许同一 adapter 声明兼容的 schema。未知字段和未知表保持目标原样，不使用反射式“合并所有表”。

跨 schema 强制同步不运行迁移或部分合并，只做完整覆盖，并要求加强确认。只有兼容矩阵明确可读的组合属于受支持操作。用户仍可对“可识别且通过完整性/关键表验证、但兼容性未知”的 Engine DJ 数据库使用高级风险覆盖；UI 必须明确无法保证目标 Engine DJ 可读取，应用后本工具验证失败即自动回滚，Engine DJ 自身兼容问题可通过保留的回滚包手动恢复。无法识别为 Engine DJ 数据库的文件始终拒绝。

## 8. 实体匹配与合并

adapter 输出稳定的 canonical entity：

- 优先使用经过验证、可跨库稳定的厂商标识。
- 曲目在歌曲可读且需要强匹配时使用忽略标签区的音频 payload hash 或经过验证的音频指纹；对象传输完整性仍使用完整文件 SHA-256，两者不得混用。客户端可使用本地身份缓存，缓存键绑定卷文件 ID、大小、修改时间和 fingerprint 版本；媒体传输和歧义匹配必须重新验证，不能为每次 database-only 预览无条件重哈希整个曲库。
- 无内容哈希时使用 adapter 认可的稳定字段，再降级到规范化路径、文件大小、时长和元数据组合。
- 多个候选匹配时标记冲突，不自动猜测。

普通同步规则：

- 源端匹配字段覆盖目标字段。
- 源端独有实体新增。
- 目标端独有实体保留。
- 不传播删除。
- 所有写入在目标快照副本的单个 SQLite 事务中执行。
- adapter 在提交前重建引用、验证外键和播放列表顺序。

类别规则必须是确定性的：播放列表以源端成员顺序为主体，目标独有成员按原目标相对顺序追加；源缺失的关系不删除目标关系。同一 cue/loop slot 冲突时源值覆盖，目标未冲突 slot 保留。对参与字段，源端 NULL/空值是明确覆盖；未选择字段保持目标。播放列表、cue/loop 和分析类别隐式依赖曲目身份读取，UI 会显示并锁定必要依赖。相同 source/target revision 和选项重复执行必须产生相同 canonical entity hash，即使 SQLite 文件布局 hash 不同。

歌曲开关开启时，只传输本次参与实体引用且实际存在的音频。目标端将歌曲放入 EngineTools 托管音乐目录，按 manifest 逻辑路径保留层级，并在暂存数据库中重写路径。

歌曲开关关闭时，匹配到目标现有曲目的记录必须保留目标路径。源端独有且目标无法定位媒体的记录写入托管目录预期路径并标记不可用，在预览中逐项统计；不能把源设备盘符直接写入目标。强制同步不带歌曲时先扫描目标已有媒体并重映射可确认匹配的路径，剩余源路径作为明确的缺失项展示并要求确认。

## 9. 差异预览与确认

目标端在暂存数据库完成模拟合并后生成预览，并记录 `target_base_hash` 与 `source_snapshot_hash`：

- 各类别新增、覆盖、保留数量。
- 冲突和被跳过实体。
- 缺失/不可读歌曲。
- 需要复制、复用、重命名和重写路径的文件数量与容量。
- 源/目标版本、捕获时间、数据库哈希和传输方式。

普通同步由发起用户确认一次。强制同步固定为二次确认：发起端先确认方向、覆盖范围和回滚要求，目标端再确认实际应用；源和目标都在当前操作端时也显示两个独立步骤。若目标是远端，远端 UI 必须显示第二次确认，发起端不能替代。

跨 schema 强制同步还要求输入目标设备显示名，并明确展示“源版本 -> 目标版本”。只有可识别为 Engine DJ、能通过 SQLite 完整性和最小关键表验证，但 schema adapter 未声明兼容的数据库才允许风险覆盖；无法验证来源或结构的文件始终拒绝。确认令牌绑定任务、快照、方向、设备、版本、`source_snapshot_hash`、`target_base_hash` 和短时有效期，防止重放。

## 10. 应用与回滚事务

目标端取得曲库写锁后：

1. 校验可用磁盘空间、manifest、全部哈希和 SQLite 完整性。
2. 创建当前数据库及受影响资产的本地回滚包；该包不计入云端配额。
3. 将歌曲和资产写入同卷暂存区，验证后准备提交。
4. 提示用户正常关闭 Engine DJ；默认等待，不直接终止进程。只有用户另行确认后才允许调用提权 Helper 终止。
5. 关闭本工具所有目标 SQLite handle，重新生成目标一致性快照并计算 base hash。若与预览绑定的 `target_base_hash` 不同，立即废弃确认、零文件提交，并重新执行合并和确认。
6. 写入带 fsync 状态的操作日志，记录每个卷、每个重命名步骤和数据库提交点。
7. 提交歌曲和资产，数据库最后通过 Windows 原子替换提交；关闭/清理旧 WAL/SHM。
8. 重新打开数据库并执行完整性、外键和 adapter 关键查询。
9. 任何失败或崩溃恢复时，根据操作日志恢复旧数据库和已替换文件。

多个文件无法跨目录/卷形成单一文件系统原子操作，因此在每个目标卷使用 sibling staging 和空间检查，以持久提交日志、数据库最后提交和启动恢复共同保证可恢复性。实现使用实际文件系统能力矩阵；不支持所需 replace/flush 语义的卷阻止任务。

目标端同时持有 durable local lock 和服务端 fencing token。控制面断线或设备撤销在 `applying/verifying/rolling_back` 阶段只设置 `revocation_pending`：本地必须完成提交或回滚，禁止新网络读取，只保留一次性终态上报 capability。此前取消会删除暂存内容并释放锁。

## 11. 任务状态

主状态：

`created -> negotiating -> snapshotting -> transferring -> staging -> preview_ready -> confirmed -> applying -> verifying -> completed`

终止状态包括 `cancelled`、`failed`、`rolled_back` 和 `manual_recovery_required`。应用后失败先进入 `rolling_back`；回滚失败进入 `manual_recovery_required`，永不自动删除最后一个已验证回滚包。

P2P/S3 是 transfer 子状态。fallback 不创建新任务，继续使用相同任务 ID、快照 ID、幂等键和已验证块。

同一目标曲库同时只有一个写任务。重复请求返回原任务，不重复覆盖。

## 12. 服务端状态与审计

PostgreSQL 的 `sync_jobs` 保存：用户、源/目标设备、模式、类别、歌曲开关、策略版本、schema、快照、状态、传输选择、确认和最终结果。

`sync_jobs` 的幂等键和目标互斥由 PostgreSQL 唯一约束及事务锁保证。确认记录、信令租约、临时传输对象和状态版本均为持久契约；Redis 只缓存在线路由和可丢进度。

Redis 保存在线 TTL、信令路由、目标 fencing/锁缓存和短时进度。真正的幂等与目标互斥由 PostgreSQL 约束和事务锁保证；Redis 丢失后可从 PostgreSQL 恢复终态，进行中的 P2P 任务安全失败或重连，不把 Redis 当最终事实。

审计记录事件码、设备、方向、版本、哈希和结果，不记录 token、签名 URL、完整歌曲路径或数据库正文。

## 13. 错误与用户体验

错误分为：认证、设备离线、策略拒绝、schema 不兼容、P2P 不可用、S3 失败、空间不足、文件锁定、校验失败、合并冲突、确认过期、应用失败和回滚失败。

每个错误具有稳定 code、可重试标识和安全文案。P2P 不可用不是用户可见失败；只有 S3 fallback 也失败时任务才失败。

设备列表使用稳定尺寸的状态行，展示设备名、在线状态、最后在线、应用/系统版本。数据库新旧信息只在用户点击同步后的预检页展示。

## 14. 测试与验收

- 两客户端集成测试覆盖 LAN host candidate、自建 STUN、公共 STUN 备用和 UDP 全阻断。
- 覆盖 P2P 探测成功、低吞吐降级、中途断线、S3 resume、重复块和损坏块。
- 合成 SQLite fixtures 验证源优先、目标独有保留、不传播删除和重复执行幂等。
- 覆盖实体歧义、播放列表层级/顺序、外键失败、路径重写和未知表保持。
- 覆盖 schema 不兼容阻止、强制风险确认过期/重放和方向交换。
- 覆盖 Engine DJ 运行、磁盘不足、只读目录、崩溃点注入和启动自动回滚。
- 覆盖预览后目标数据库变化导致旧确认失效，且零文件被替换。
- 覆盖 WAL/SHM、busy/locked、快照中途写入和关闭全部 handle 后重验 base hash。
- 覆盖不带歌曲时路径相同、盘符变化、部分媒体可复用和全部媒体不可定位。
- 覆盖 ID3-only 修改不制造重复曲目，以及各类别确定性规则的幂等 canonical hash。
- 覆盖 transferring/preview_ready/applying 各阶段离线、撤销、服务端重启和 Redis 丢失。
- 大库测试验证打包、哈希和传输为流式处理，内存不随总歌曲容量线性增长。

## 15. 完成标准

两台在线设备可在不创建后台同步快照的前提下完成 P2P 优先、S3 fallback 的手动同步；普通同步结果满足源优先且不删除目标独有内容；强制同步有明确方向、目标本地确认和可验证回滚；失败不能留下不可打开的数据库。独立的自动周备份不改变这一同步触发规则。

## 16. 相关规格与顺序

本规格依赖桌面安全基础以及中心服务/设备/备份规格。ID3 编辑器规格独立实施，但共享结构化任务结果、托管音乐目录和文件安全写入约束。
